Technical specification · v3 · Terra Classic · BSC · Ethereum · Solana

Remuneration of multiple Relayers
on the Hyperlane bridge

An operator is not paid because it configured an IGP. It is paid because it delivered the message. On three of the four networks this is proven by Hyperlane's own core; on the fourth, by consensus among operators. Each network pays in its own currency, with the money its users have already paid — no budget, no foreign-currency treasury, and without modifying a single line of the protocol.

01

Executive summary

The Terra Classic Hyperlane bridge has no operators: the existing IGPs serve other routes. To operate in a decentralized way, several relayers must work in parallel, each paid for what it delivered — no registration, no approved list, and without an idle operator being paid.

Single rule

The operator's economic identity is the network's own execution record, never a claim it makes. Where the network does not record it, operators in quorum must agree on what the public chain shows.

Funding

Each network has its own Vault, the beneficiary of the local IGP. Whoever dispatches from that network pays for the deliveries made on it. The pool grows with usage and never becomes insolvent as long as the fee is smaller than the average revenue.

Not a single line of the core is modified. Mailbox, ISM, IGP, oracle and Warp Route remain as in upstream. Only the configuration changes: the beneficiary of each IGP becomes the Vault and, on Solana, ownership of the IGP passes to the governor program.

Governance model

Three spheres with scopes that do not overlap. The principle: what is operational stays with those who operate; what is structural stays with those who hold a mandate.

┌────────────────────────────────────────────────────────────┐ │ TERRA CLASSIC GOVERNANCE │ │ on-chain proposal · scope: everything within Terra Classic│ │ IGP · ISM · Vault · Oracle · fee · bounds │ └──────────────────────────┬─────────────────────────────────┘ │ grants mandate via approved proposal ▼ ┌────────────────────────────────────────────────────────────┐ │ HYPERLANE VALIDATORS MULTISIG │ │ BSC · Ethereum · Solana │ │ scope: IGP · ISM · oracle bounds │ └──────────────────────────┬─────────────────────────────────┘ │ ▼ ┌────────────────────────────────────────────────────────────┐ │ RELAYER OPERATORS (on-chain quorum, no multisig) │ │ scope: Vault and Oracle on the remote networks │ │ · update price within bounds │ │ · epoch reports (Solana) │ │ · Vault parameters, via proposal with quorum │ └────────────────────────────────────────────────────────────┘ delivering messages: OPEN TO ANYONE, no permission
Why on-chain quorum and not a wallet multisig. With a multisig, the operators would have to coordinate signing the same transaction four times a day. With on-chain quorum, each one submits its own independently and the program resolves the convergence. Less operational friction and the same level of protection.
Mandatory separation in the multisig. The operators also sign the ISM checkpoints. If they are the only signatories of the multisig that controls the ISM, a collusion could forge messages and alter the verification rules. The multisig needs signatories who are not Hyperlane validators.
05

Economic principle

Each network sustains itself. The gas spent and the payment received happen in the same currency, on the same chain.

TC → BSC BSC → TC ───────── ───────── user pays LUNC on TC user pays BNB on BSC relayer spends BNB on BSC relayer spends LUNC on TC BSC Vault pays in BNB TC Vault pays in LUNC (from the BNB of whoever (from the LUNC of whoever dispatches from BSC) dispatches from TC)
Self-funded by construction. Without usage there is no revenue — but there was also no work. With usage, the pool grows alongside it. No budget is needed.
Contingency for asymmetry. If almost all traffic leaves Terra Classic, the remote pools collect little. In that case the epoch mechanism starts to remunerate the remote leg in LUNC, from the TC pool. Provided for in the proposal, built only if the numbers require it.

Terra Classic · CosmWasm

local proof · storage read

The Mailbox records the executor, but the public query MessageDelivered uses .has() and discards the address. The data exists — it is just not exposed.

// hpl-mailbox · execute::process
DELIVERIES.save(storage, id, &Delivery {
    sender: info.sender,          ← who signed the transaction
    block_number: env.block.height,
})?;

// raw key of Map<Vec<u8>, _> from cw-storage-plus
[0x00, 0x0A] + b"deliveries" + message_id(32 bytes)
// empty = not delivered; also replaces MessageDelivered

Flow of a delivery

message arrives → the relayers compete over process() 1st in the block records its address · the others revert │ ▼ raw query Vault::Claim { message_ids } · not yet claimed? · sender == requester? · within the window? · marks as paid (effect) · checks solvency · BankMsg::Send

Specifics

  • The IGP claim() only accepts the beneficiary → the Vault needs Sweep, which is permissionless and usually goes in the same transaction as the withdrawal
  • Owner is the on-chain governance, not a multisig
  • This is where the real collateral that backs the synthetics on the other networks resides
  • A claim batch is atomic: one invalid id reverts everything without consuming the valid ones
Specific fragility. A Mailbox migrate may change the storage layout. The LayoutCheck query must be monitored: the contract fails with MailboxLayoutMismatch instead of paying incorrectly. The test has to be run against the wasm in production, not against upstream main.

BSC and Ethereum · EVM

local proof · direct query

The simplest case. The v3 Mailbox.sol exposes everything the Vault needs.

address processor = mailbox.processor(id);
if (processor == address(0)) revert NotDelivered(id);
if (processor != msg.sender) revert NotProcessor(id, processor);

uint256 deadline = mailbox.processedAt(id) + claimWindowBlocks;

Specifics

  • receive() payable is mandatory: without it the IGP claim() reverts
  • ISM and IGP associated with the synthetic Warp — the Warp quotes and pays on its own
  • GasOracleGovernor becomes owner of the StorageGasOracle: a clean separation, because the oracle is an independent contract
  • 6h epochs derived from block.timestamp, with no coordination between operators
The IGP tied to the Warp resolves optional payment. Since the Warp Route quotes and pays the IGP before dispatching, the revenue is enforced by the token flow — regardless of which hook is configured as required_hook in the Mailbox.
08

Solana · Sealevel

no local proof · operator quorum

The exception. The program creates a PDA per processed message — which prevents reprocessing — but does not store who created it:

pub struct ProcessedMessage {
    discriminator: [u8; 8],
    sequence: u64,
    message_id: H256,
    slot: Slot,                 ← no executor field
}   size = 56 bytes

The payer signs and pays the rent, but that information is discarded. Merely checking whether the PDA exists would let another operator claim the credit — this is why authorship comes from the quorum.

Two programs

RelayerRewardVault

The config PDA is the pool — register it as the IGP beneficiary. Epochs with quorum, per-operator credits, withdrawal by direct debit of lamports while respecting rent-exempt. Does not touch the Mailbox or the IGP.

IgpOracleGovernor

Becomes owner of the IGP and rebuilds the separation of powers that the chain does not offer natively. Two gates with distinct authorizations.

Why the governor is necessary

On Solana the oracle is NOT a separate contract: Igp { bump, salt, owner, beneficiary, gas_oracles: HashMap } SetGasOracleConfigs requires ensure_owner_signer(owner) → whoever updates the price is necessarily the IGP owner → and the owner also controls beneficiary and transfer ┌──────────────────────────────────────────────┐ │ IgpOracleGovernor (IGP owner) │ ├──────────────────────────────────────────────┤ │ GATE 1 · operators, quorum + median │ │ SubmitPrice → CPI SetGasOracleConfigs │ ├──────────────────────────────────────────────┤ │ GATE 2 · multisig, single signature │ │ SetBounds │ │ SetIgpBeneficiary │ │ TransferIgpOwnership ← emergency exit │ └──────────────────────────────────────────────┘
The separation becomes logical, not cryptographic. Before, without the multisig key there was no way to touch the IGP. With the governor, it is its code that prevents it. Three mandatory consequences: TransferIgpOwnership implemented and tested before deploy; the config PDA must keep lamports (the IGP realloc charges the owner); and the program's upgrade authority must be the multisig, otherwise everything is circumventable by redeploy.
Separate calibration. The relayer pays the rent of the processed-message PDA on top of the fee, so the fee on Solana is proportionally higher. And TOKEN_EXCHANGE_RATE_SCALE is 10¹⁹ on Solana versus 10¹⁰ on EVM — the bounds must be recalculated, not copied. token_decimals is a network constant and stays with the multisig, outside the quorum.
09

Quorum: epochs and proposals

The same mechanism serves two purposes: assigning credit for remote deliveries and approving administrative changes. A single trust model across the whole system.

Delivery epochs

00:00 06:00 12:00 18:00 00:00 UTC │────epoch 0───│────epoch 1───│────epoch 2───│────epoch 3───│ │ + confirmation slack (reorg / finality) ▼ ┌────────────┼────────────┐ hash A hash B hash C └──────┬─────┘ │ quorum of identical hashes → credits assigned └─ divergence → epoch locked, alarm, manual resolution

Two rules prevent convergence failures that are not bad faith: the delivery list must come ordered by key (otherwise the same content in different orders would produce distinct hashes), and the block window becomes immutable after the first submission (otherwise an operator would pick a convenient interval).

Administrative proposals

There is no single admin in the Vault. Any parameter change is a proposal that requires the same quorum:

SubmitAdminAction(AdminEnvelope { nonce, action })

// the envelope hash IS the PDA seed — all operators
// converge on the same account without agreeing anything beforehand
seeds = ["rrv", "-", "prop", "-", hash(envelope)]

The nonce

Allows repeating an identical action in the future — pause, unpause, pause again — without colliding with the previous, already-executed proposal.

Destination in the hash

In WithdrawSurplus, the destination address is part of the hash. The operators approve that address, not a generic withdrawal that the last to sign could redirect.

Known limit. A collusion that reaches the quorum can report whatever it wants. It is the same threshold as the ISM that already underpins the bridge — not a new risk, but it must be explicit in the proposal. Anyone can audit the report against the public chain and report a divergence.

Oracle across the four networks

A lagging gas price and exchange rate make the quote charge too little (the pool dries up) or too much (the bridge becomes expensive). The pattern is the same on all networks; the implementation changes.

governance / multisig ── sets ──▶ bounds [min,max] + max variation │ locked on-chain operator A ─┐ ▼ operator B ─┼── SubmitPrice ──▶ ┌──────────────────────┐ operator C ─┘ │ Governor │ │ median │ │ within bounds? │ │ delta < limit? │ └──────────┬───────────┘ ▼ network oracle

Median, not identical hash

Price is a market observation, not a verifiable fact: honest agents see slightly different numbers. Requiring equality would lock the oracle. With an even number of submissions, the lower of the two central ones is used — when in doubt it charges the user less.

Bounds and variation limit

Outside the bounds, it rejects. A jump above the per-epoch limit (suggestion: 2000 bps), it rejects. Protects against RPC error and abrupt movement, without human supervision.

The conflict of interest that the bounds neutralize. The operators control the price that funds their own remuneration: an inflated exchange rate makes the user pay more to the IGP, fattening the pool that pays them. Since the bounds are set by governance (on TC) or by the multisig (on the remotes) — never by the operators themselves — they are a real lock and not just a record.
Emergency path on all networks. Governance and multisig retain the ability to write directly to the oracle should the governor fail. Without this second gate, a bug would lock the pricing of the entire bridge.

The most serious risk is not in the Vault. The real collateral is locked on Terra Classic and the synthetic is minted on the remote networks. Whoever controls the remote Warp's ISM controls the minting: a tampered ISM allows minting synthetic without backing, burning it, and the burn message that reaches Terra Classic is legitimate — the honest ISM on the TC side will validate it and release real collateral.

The multisig that administers the remote ISM therefore has indirect access to the collateral. It requires proportional protections: never composed solely of the validators who sign checkpoints, and ideally with a timelock on ISM swaps. This is not solved in a contract — it is solved in the composition of the multisig and in the text of the proposal.

Deployment

PHASE 0

Verification on mainnet

Read the DELIVERIES of a real message already delivered on Terra Classic. Check the Mailbox hooks and the data_hash of the deployed code against the repository. Nothing is written or deployed before this.

PHASE 1

Oracle on Terra Classic

OracleGovernor + agent running only the price module. It is mandatory anyway and validates whether the operators can keep the process running. Failures here are reversible.

PHASE 2

Vault on Terra Classic

Deploy, IGP.beneficiary = Vault, payment of local deliveries. Does not depend on the agent.

PHASE 3

BSC and Ethereum

Vault and GasOracleGovernor in Solidity, multisig configured, beneficiary pointed, oracle transferred to the governor. Direct local proof, no agent and no epochs.

PHASE 4

Solana

Vault with epochs first — it is independent and does not touch the IGP. Only then the governor, testing the emergency exit before transferring ownership. In parallel: external audit and expansion of the validator set.

Checklist per network

// Terra Classic
1. deploy the Vault          4. governance: IGP.beneficiary = Vault
2. deploy the OracleGovernor 5. governance: Oracle.owner = Governor
3. seed the pool             6. monitor LayoutCheck

// BSC / Ethereum
1. deploy the Vault (owner = multisig)
2. deploy the GasOracleGovernor + setBounds
3. transferOwnership of the StorageGasOracle → Governor
4. multisig: IGP.beneficiary = Vault

// Solana
1. deploy the Vault + Init     → config PDA = beneficiary
2. deploy the Governor + Init  → SetBounds by the multisig
3. TEST TransferIgpOwnership on devnet
4. transfer IGP ownership to the Governor
5. Governor upgrade authority → multisig
